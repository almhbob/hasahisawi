6. الأمان والمصادقة

طبقات المصادقة

  1. Firebase Authentication — للمستخدم النهائي (Email/Password, Google Sign-In, Phone).
  2. Backend JWT Sessions — يصدر الخادم session token بعد التحقّق من الـ ID token عبر Firebase Admin.
  3. x-user-token — Header لكل طلب محمي.
  4. x-admin-pin — لمسارات الإدارة الحساسة.

Rate Limiting (express-rate-limit)

المسارالنافذةالحد
عام (كل المسارات)15 دقيقة300 طلب / IP
تسجيل الدخول15 دقيقة10 محاولات فاشلة
التحقّق من PIN الإدارة10 دقائق5 محاولات

هيدرز الأمان (Helmet)

  • مفعّل افتراضياً مع تخصيص crossOriginResourcePolicy: cross-origin ليسمح بتقديم ملفات /uploads للموبايل.
  • CSP موقوف لأن التطبيق Native (لا يمر عبر متصفح).

CORS

مفعّل لكل الـ origins (origin: true) — الحماية الفعلية عبر Bearer tokens، لأن React Native لا يرسل Origin ثابت.

قائمة فحص الأمان قبل كل إصدار

  • التأكد من عدم تسريب FIREBASE_SERVICE_ACCOUNT_JSON في أي ملف.
  • التأكد من تشغيل npm audit أو فحص أمان dependencies.
  • التأكد من تحديث Firebase Security Rules (Storage + Firestore).
  • تدوير ADMIN_PIN دورياً (كل 90 يوم).
  • مراجعة SHA-1 في Firebase Console مطابق لمفتاح التوقيع.

8. قاعدة البيانات والمخطط

  • المحرّك: PostgreSQL (Render في الإنتاج، محلي في التطوير).
  • ORM / Schema: Drizzle — artifacts/hasahisawi/shared/schema.ts
  • Migrations: drizzle-kit — مجلد migrations/
  • أمر فحص: npx drizzle-kit push أو generate
  • التحقّق من المدخلات: Zod + drizzle-zod (آلياً).

قواعد قبل أي تعديل على المخطط

  1. أنشئ migration بـ drizzle-kit generate، لا تعدّل قاعدة الإنتاج يدوياً.
  2. اختبر الـ migration على نسخة محليّة أولاً.
  3. خذ نسخة احتياطية قبل التطبيق على الإنتاج.
  4. أضف الحقل كـ nullable أوّلاً، ثم اجعله مطلوباً في إصدار لاحق (zero-downtime).

13. قائمة فحص ما قبل النشر

اتّبع هذه الخطوات قبل كل إصدار جديد بدون استثناء:
  1. ارفع android.versionCode بـ +1 على الأقل، وحدّث version الدلالي (5.6.5 → 5.6.6).
  2. حدّث ios.buildNumber إذا كنت ستبني iOS.
  3. شغّل pnpm typecheck — يجب أن يمرّ بدون أخطاء.
  4. اختبر تسجيل الدخول، رفع صورة، رفع فيديو، إرسال إشعار.
  5. تأكّد أن EXPO_PUBLIC_API_URL يشير إلى الإنتاج وليس Replit dev.
  6. تأكّد من تطابق SHA-1 في Firebase Console مع مفتاح التوقيع.
  7. راجع Firebase Security Rules (Storage + Firestore).
  8. افحص Render logs بعد آخر deploy للتأكد من عدم وجود أخطاء حرجة.
  9. تحقّق من app/version و app/feature-flags أنّها صحيحة.
  10. اعمل APK preview أوّلاً واختبره على جهاز فعلي قبل بناء AAB للنشر.
  11. خذ نسخة احتياطية من قاعدة البيانات.
  12. دوّن الإصدار الجديد في CHANGELOG (إن وُجد).

  • التطبيق يعرض شاشة "حدّث التطبيق" تلقائياً عند المقارنة.

17. إجراءات الطوارئ (Rollback & Recovery)

إذا فشل النشر على Render

  1. افتح Render Dashboard → Service → Manual Deploy → اختر آخر deploy ناجح → Rollback.
  2. أو عبر API: POST /v1/services/{id}/rollback باستخدام RENDER_API_KEY.
  3. افحص logs لمعرفة سبب الفشل قبل المحاولة الثانية.

إذا تعطّل التطبيق بعد إصدار

  1. اقلب feature flag للميزة المتسبّبة عبر /admin/feature-flags فوراً.
  2. إذا كان التعطّل عام، فعّل Force Update برفع min_supported.
  3. ابنِ نسخة hotfix بـ versionCode أعلى وانشرها.

إذا فُقد مفتاح التوقيع

كارثة: لن تستطيع تحديث التطبيق على نفس الـ package. يجب نشر تطبيق جديد بـ package مختلف وفقدان جميع التقييمات والمستخدمين الحاليين.
الوقاية: احتفظ بنسخ من credentials.json + .pem في 3 أماكن منفصلة (محلي، Drive، USB مشفّر). فعّل Play App Signing من Google لتقليل الخطر.

إذا تسرّب FIREBASE_SERVICE_ACCOUNT_JSON

  1. افتح Firebase Console → Settings → Service Accounts.
  2. احذف المفتاح المسرّب فوراً.
  3. أنشئ مفتاحاً جديداً وحدّث FIREBASE_SERVICE_ACCOUNT_JSON على Render.
  4. أعد تشغيل الخادم.
  5. دقّق سجلّات الوصول للتأكد من عدم سوء استخدام.

إذا تعطّلت قاعدة البيانات

  1. افتح Render Dashboard → Database → Backups → استعد آخر نسخة.
  2. استخدم pg_restore إذا كان لديك نسخة محلية.
  3. الخادم سيرجع تلقائياً عند توفّر القاعدة (لا rebuild مطلوب).
